# 重构评估

## 总览
- `cargo check --workspace` 已可顺利执行，但产生大量 `dead_code`、`unused_variables` 警告
- 多个策略 crate 尚处于占位状态，仅定义数据结构和接口
- 客户端、策略与执行器之间存在相似的适配代码，可通过抽象层减少重复

## 主要问题
1. **模块重复与耦合度**
   - 目录中同时存在 `crates/core/clients/opensea-v2` 与 `crates/clients/opensea-v2` 两套实现，易造成维护混乱
   - `bin/artemis` 直接依赖核心库内部细节（如具体 Collector、Executor），缺少统一配置层
2. **占位代码较多**
   - `crates/strategies/mev-arbitrage`、`strategies/defi-analyzer` 中大量字段未被访问
   - `symbolic-execution` 模块包含大段未完成的路径处理逻辑
3. **配置分散**
   - 目前需要通过命令行参数或 `.env` 手动传递多个关键变量，缺乏集中式配置管理
4. **测试覆盖不足**
   - `tests/` 下缺少针对复杂策略的回归案例，难以保证重构后逻辑一致
5. **性能路径缺乏隔离**
   - Engine 中 Collector、Strategy、Executor 共享同一 Tokio runtime，未对高频任务做优先级控制

## 建议的重构方向
- **抽象配置层**（高优先级）
  - 引入 `Config` crate，集中管理节点、密钥、策略参数，支持从文件/环境变量加载
  - 将 `bin/artemis` 中的参数解析逻辑迁移至配置层，主程序只负责装配
- **整合客户端实现**（中优先级）
  - 对比两套 OpenSea 客户端，确认差异后保留其中一套，并在核心库通过 trait 暴露统一接口
- **策略模块瘦身**（高优先级）
  - 将 `dead_code` 字段按职责拆分至独立组件，或在特性标记下延迟编译
  - 明确符号执行、图论模块的输入输出契约，减少耦合
- **引入分层测试**（中优先级）
  - 为关键策略补充模拟链路测试（Collector→Strategy→Executor）
  - 利用 `proptest` 或静态样例覆盖边界场景
- **执行路径隔离**（低优先级）
  - 针对高频 Collector 建立专用 Tokio Runtime 或使用优先级队列
  - 考虑在 Engine 中加入背压指标，避免长尾任务阻塞主循环

## 近期可实施的行动项
1. 清理未使用字段，利用 `cargo clippy -- -D warnings` 逼迫代码收敛
2. 引入 `serde` + `config` crate，构建 `config/default.toml` 并支持覆盖
3. 合并重复客户端模块，并补充集成测试确保行为一致
4. 针对 `mev-arbitrage` 策略梳理真实使用路径，补齐缺失实现或拆分占位模块

该评估基于当前仓库结构与一次 `cargo check` 结果，建议在落实重构前再次回顾业务需求与运行环境。
